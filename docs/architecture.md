# Архитектура AKCP

AKCP построен как монолит с модульной структурой и «hexagonal‑ish» границами:

- Контроллеры → Сервисы → Репозитории
- Доменные модели в `akcp-core`
- Отдельные модули по зонам ответственности (ingestion, library, publishing, jobs, auth)

## Основные домены

- **Item** — единица контента (текст + источник + вложения)
- **Attachment** — вложение (в MVP — изображения)
- **Tag** — метка для фильтрации
- **Job** — фоновые операции (публикация, вычисления pHash/эмбеддингов)
- **SourceRef / PublishTarget** — ссылки на источники/цели

## Потоки данных (MVP)

1. Ingestion Web → парсинг URL → Item + Attachments
2. Library → CRUD Item/Tags → хранение в Postgres
3. Publishing VK → постановка Job → JobRunner → заглушка

## Хранилище

PostgreSQL + Flyway миграции. R2DBC используется для реактивного доступа.

## Границы модулей

`akcp-app` является единственной точкой сборки Spring Boot: здесь находятся
конфигурация, миграции и wiring адаптеров. Остальные модули не должны зависеть
от `akcp-app` или друг от друга через реализационные классы.

- `akcp-core` содержит доменные типы и порты. Он не знает о Spring, Postgres,
  VK и HTTP.
- `akcp-library` реализует каталог контента и операции библиотеки через порты
  core; persistence-код остаётся внутри модуля.
- `akcp-ingestion-web` принимает web-источники, выполняет bounded parsing и
  передаёт результат в библиотеку/порты.
- `akcp-publishing-vk` содержит VK boundary, publish job и адаптеры. Реальные
  credentials не являются частью репозитория.
- `akcp-jobs` отвечает за хранение, lease/claim и запуск фоновых задач.
- `akcp-auth` отвечает за JWT и роли; он не должен становиться способом обхода
  доменных проверок в других модулях.

При добавлении функциональности сначала выбирается доменный порт в `akcp-core`,
затем реализация в профильном модуле, а подключение выполняется в `akcp-app`.
Такой порядок сохраняет возможность тестировать доменную логику без Postgres и
Docker.

`.env`, credentials, certificates, generated logs и другие локальные артефакты.
